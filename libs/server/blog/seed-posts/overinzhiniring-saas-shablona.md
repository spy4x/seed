Что я сделал не так в Seed v1? Я его переусложнил: построил леса для большого продукта раньше
самого продукта. Это видно по его же роадмапу. Из 66 пунктов отмечены 33, и отмеченная половина —
в основном инструменты и серверная обвязка: монорепозиторий, строгие правила линтера, pre-commit
хук, базовые классы CQRS, деплой в Google Cloud. Во второй половине осталось почти всё, чем
пользуется человек: группы, платежи, обновления в реальном времени, офлайн, загрузка файлов и
админка.

Пост для разработчиков, которые пишут свой SaaS-шаблон или первый SaaS и подозревают, что полируют
мастерскую вместо того, чтобы делать мебель. Каждая цифра ниже взята из кода: v1 до сих пор лежит в
репозитории под тегом [`v1-final`](https://github.com/spy4x/seed/tree/v1-final), а команды, которыми
я считал, — в [пулл-реквесте](https://github.com/spy4x/seed/pull/823) с этим постом. Ни одно
воспоминание не пострадало: я просто посчитал.

## Каким был Seed v1?

«Full-stack startup monorepo template», как писал его README, с лучшими практиками с первого дня.
Angular на фронтенде, Nest.js и Prisma на PostgreSQL на бэкенде, Firebase для входа, Google Cloud
для запуска, Nx, чтобы всё это держать вместе, и Yarn для установки. Первый коммит — 16 июня 2019
года, последний — 23 декабря 2022-го: 134 коммита за три с половиной года.

Он не затух постепенно, а остановился: 55 коммитов пришлись на последние два месяца, а потом
ничего, пока 26 января 2026 года Seed не начался заново, с новой историей.

## Что обещал роадмап и что было сделано?

Роадмап в README отмечал каждый пункт как сделанный или запланированный. Последний раз его
обновляли 25 ноября 2022 года:

| Раздел роадмапа                         | Сделано | В планах |
| --------------------------------------- | ------: | -------: |
| Окружение и организация кода            |       8 |        7 |
| Бэкенд                                  |      14 |        5 |
| База данных                             |       3 |        1 |
| Общий фронтенд (вход, состояние, тесты) |       6 |        3 |
| Стили                                   |       2 |        0 |
| PWA (офлайн, пуши, установка)           |       0 |        4 |
| Загрузка файлов                         |       0 |        4 |
| Админка                                 |       0 |        3 |
| Веб-клиент (группы, realtime, аккаунт)  |       0 |        6 |
| **Итого**                               |  **33** |   **33** |

Подписки Stripe стояли в разделе бэкенда, в планах. Таблица пользователей для админки всё же
появилась в декабре 2022-го, уже после последнего обновления роадмапа, так что засчитаем v1 и её.

Три из 33 галочек — автоматические бэкапы, восстановление из бэкапа и реплики для чтения. Каждая
вела на документацию Google Cloud SQL, а документ об инфраструктуре честно говорил, что репликация
«not yet used». Я отмечал домашку, которую сделал Google.

## Куда вместо этого ушла работа?

В мастерскую. У коммитов есть тип, и он рассказывает эту историю лучше меня:

- **52 из 134 коммитов имеют тип `env` или `environment`**: конфиги, инструменты, CI, обновления
  и переименования. Типа `feat` — 31.
- **Первый коммит, после которого человек может хоть что-то сделать** (простое API пользователей:
  регистрация, «кто я», обновить себя), — 38-й, от 31 мая 2021 года, почти через два года после
  первого. Среди первых 37 — 28 коммитов `environment`.
- **CI настраивали трижды**: GitLab CI в июле 2019-го, GitHub Actions в марте 2021-го, Google
  Cloud Build в июне 2021-го. В последней версии роадмапа CI/CD всё ещё числился в планах.
- **Четыре переименования приложений и папок за два дня** в феврале 2021-го и коммит под
  названием «massive refactoring» через год.

## Сколько структуры на сколько данных?

В схеме базы v1 три модели: `User`, `UserDevice` и `Notification`. Вокруг них:

- **31 проект Nx**: три приложения, два приложения для e2e-тестов и 26 библиотек. Один только
  общий вход на фронтенде — это четыре библиотеки: container, guards, state и UI.
- **65 файлов `index.ts`**, и 63 из них только реэкспортируют другие файлы.
- **Слой CQRS со своими базовыми классами** поверх шин команд, запросов и событий: 11 команд,
  5 запросов и 7 событий, к ним 19 обработчиков.
- **Девять облачных сервисов** в документе об инфраструктуре (Cloud Run, Cloud SQL, Cloud Tasks,
  Cloud Logging, Cloud IAM, Firebase Authentication, Hosting и Storage, плюс Sentry) и инструкция
  по настройке с пометкой «WIP», которая начиналась с ручных шагов.
- **104 npm-пакета** в корневом `package.json`, из них 50 — зависимости времени выполнения.

Для сравнения: в сегодняшнем Seed 34 пакета в workspace на 73 таблицы. Структура теперь растёт
вместе с данными, а не ждёт их.

## Может, проблема в том, что фич было слишком много?

Нет, и это то, что я хочу сказать точно. Оверинжиниринг — это когда фичу строят сложнее, чем ей
нужно: лишние слои, защита от редких гонок, автоматизация, которую никто не запускает. Это не
«эта фича не нужна». Список желаний v1 был нормальным. В сегодняшнем Seed есть все продуктовые
фичи, которые v1 только планировал, и больше: passkeys и второй фактор, группы с ролями и
приглашениями, оплата Stripe за каждого участника, обновления в реальном времени, офлайн-приложение,
хранилище файлов, админка на своём домене и девять языков
([README](https://github.com/spy4x/seed#readme)).

Seed даже по-прежнему использует CQRS: у команд, запросов и событий по своей шине, а каждое
изменение группы пишет событие в outbox, который разбирает воркер. Паттерн ни в чём не виноват.
Виноваты четыре библиотеки для входа, написанные раньше, чем появилась хоть одна группа.

## Что Seed делает иначе теперь?

- **Один образец для каждой фичи.** Новая фича копирует заметки файл за файлом, в заданном
  порядке: [все файлы агрегата заметок](/ru/docs/aggregates). Руководство говорит прямо: «Do not
  invent a second shape» — не придумывайте вторую форму.
- **Один сервер вместо девяти сервисов.** Docker Compose запускает приложение, Postgres, прокси и
  мониторинг на сервере, которым вы управляете:
  [развернуть SaaS на одном сервере Hetzner](/ru/blog/razvernut-saas-na-odnom-servere-hetzner).
- **Принципы, которые говорят «нет».** В
  [принципах Seed](https://github.com/spy4x/seed/blob/main/docs/principles.md) есть «Ship small,
  safe slices», «Avoid speculative complexity» и «Add deps only with clear ROI»: выпускать
  маленькими безопасными кусками, не строить сложность на всякий случай, добавлять зависимость
  только когда она явно окупается.
- **Веб-стандарты вместо фреймворков.** Серверы говорят на Fetch, Web Crypto и WebSocket, а не на
  закрытом API одной платформы:
  [почему Seed построен на веб-стандартах](/ru/blog/pochemu-seed-besplatnyj-saas-starter-na-veb-standartah).

Типы коммитов тоже сдвинулись. Из 531 коммита Seed после перезапуска 194 — `feat` и 46 — `chore`,
`ci` или `build`. Почти все они — пулл-реквесты, слитые через squash, так что по размеру они не
равны коммитам v1, но направление видно.

## Не делает ли ваш шаблон то же самое?

Три быстрые проверки по цифрам v1 выше:

1. Посчитайте папки и таблицы. Библиотек больше, чем таблиц, — повод насторожиться.
2. Прочитайте половину роадмапа «в планах». Если там всё, чего коснётся пользователь, вы строите
   мастерскую.
3. Найдите коммит, после которого человек впервые смог что-то сделать. Если это 38-й — привет,
   это я.

Или пропустите леса: [Seed](https://github.com/spy4x/seed) бесплатный, под лицензией MIT, и его
фундамент уже построен. Склонируйте его и
[сделайте первую фичу](/blog/your-first-feature-copy-the-notes-aggregate) на этой неделе (пост на
английском).
